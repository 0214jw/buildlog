# BuildLog MVP 개발 계획

## 1. 계획의 목적과 기준

2026-10-26 Phase 0 확인 결과는 [phase-0.md](phase-0.md)에 기록했습니다. 환경·문서 점검과 기술 기본안 정리는 수행했으며 인증 등 사용자 결정은 남아 있습니다. 현재 상태는 **점검 완료·결정 대기**입니다. Phase 1은 아직 시작하지 않았습니다. 실행 환경과 예정 명령은 [setup.md](setup.md)를 따릅니다.

이 문서는 `PRD.md`와 `spec.md`의 기능을 어떤 순서로 개발할지 설명합니다. 백엔드는 FastAPI, 프론트엔드는 React, 실제 서비스 DB는 Supabase를 사용합니다. 처음에는 SQLite3로 개발·테스트합니다.

한 번의 작업에서는 Phase 하나만 진행합니다. 확인 기준을 통과한 뒤 결과를 공유하고 사용자가 확인하면 다음 Phase로 넘어갑니다. 이 계획을 수정하는 단계에서는 설치나 구현을 시작하지 않습니다.

## 2. 개발 원칙

- 문서에 없는 제품 기능을 추가하지 않습니다.
- 각 Phase에서 해당 범위의 자동 테스트와 직접 화면 확인을 수행합니다. 화면이 없는 단계에서는 API나 데이터 결과로 확인합니다.
- 실패한 확인 항목을 수정한 뒤 다음 Phase로 넘어갑니다.
- React에서 버튼을 숨기는 것과 별개로 FastAPI에서도 사용자와 대상 기록의 권한을 검사합니다.
- React는 FastAPI에 데이터 처리를 요청하는 구조로 만듭니다. 화면에서 DB에 직접 접근하는 구조는 기본 계획에 포함하지 않습니다.
- 비밀번호 원문을 저장하지 않습니다. DB 연결 비밀값과 서버 전용 키를 코드나 React 화면에 넣지 않습니다.
- SQLite3 파일, 실제 `.env`와 `.env.*`, 가상환경, 설치 폴더, 빌드 결과, 로그는 Git 기록 대상에서 제외하고 비밀값 없는 `.env.example`은 기록할 수 있게 합니다.
- Git 초기화와 커밋은 별도 요청 전까지 하지 않습니다.
- Django 프로젝트·템플릿·사용자 모델·관리자 화면을 사용하지 않습니다.
- 필요한 패키지, 데이터 연결 도구와 버전은 Phase 0에서 검토하고 해당 구현 단계에서 설치합니다.
- SQLite3 통과를 Supabase 통과로 간주하지 않습니다. Supabase 실제 연결 확인까지 계획에 포함합니다.
- 이 문서의 작업은 예정이며 이미 실행하거나 완료한 것이 아닙니다.

## 3. 예정된 프로젝트 구조

```text
buildlog/
├─ backend/
│  ├─ requirements.txt
│  ├─ app/
│  │  ├─ main.py          # FastAPI 시작점
│  │  ├─ core/            # 환경 설정, 인증·권한 공통 처리
│  │  ├─ db/              # 환경별 DB 연결
│  │  ├─ accounts/        # 회원가입·로그인·닉네임 API
│  │  ├─ records/         # 공부 기록·할 일·오류 기록 API
│  │  └─ community/       # 댓글·좋아요·신고 API
│  ├─ migrations/         # DB 구조 변경 관리. 도구는 Phase 0에서 결정
│  └─ tests/
├─ frontend/
│  ├─ package.json
│  ├─ src/
│  │  ├─ pages/           # React 화면
│  │  ├─ components/      # 공통 카드·입력·메뉴
│  │  ├─ api/             # FastAPI 요청 처리
│  │  └─ styles/          # 공통 디자인과 반응형 CSS
│  └─ public/
├─ database/
│  └─ buildlog.sqlite3    # 로컬 개발·테스트용. Git 제외
└─ docs/
```

실제 Supabase 데이터는 위 SQLite3 파일에 저장하지 않습니다. 테스트는 별도 임시 SQLite3 DB를 사용해 로컬 개발 데이터를 훼손하지 않도록 합니다. React 프로젝트 생성 도구와 세부 설정 파일은 Phase 0에서 정합니다.

## 5. Phase별 상세 계획

### Phase 0. 개발 전 문서와 실행 환경 확인

**목표:** 코드를 만들기 전에 개발 기준을 맞춥니다.

**작업 순서**

1. PRD·spec·plan의 기능 범위와 기술 구성이 일치하는지 확인합니다.
2. 기존 계획에서 구체적으로 정했지만 spec에서는 확인 필요인 조건을 대조합니다. 아래 6절의 항목은 확정 여부를 확인한 뒤 spec에 반영합니다.
3. 설치된 Python, Node.js, npm 버전과 Python의 SQLite3 사용 가능 여부를 읽기 전용으로 확인합니다.
4. 호환되는 FastAPI·React와 필요한 실행·DB 도구의 버전을 검토합니다.
5. FastAPI가 회원 인증을 직접 처리할지 Supabase Auth를 사용할지 결정합니다. SQLite3 환경에서 인증을 어떻게 테스트할지도 함께 정합니다.
6. DB 연결 방식과 DB 구조 변경 관리 도구를 정합니다. SQLite3와 Supabase 양쪽을 지원하는지 확인합니다.
7. 운영자가 신고를 확인할 방법을 정합니다. Django 관리자 화면을 전제로 하지 않습니다.
8. 개발 주소의 기본안은 FastAPI `http://127.0.0.1:8000`, React `http://localhost:5173`으로 두고 사용 가능 여부를 확인합니다. React 생성 도구에 따라 포트는 확정합니다.
9. 실제 DB는 Supabase, 로컬 개발 DB는 `database/buildlog.sqlite3`, 자동 테스트는 별도 임시 DB로 구분합니다.
10. 서버와 프론트가 각각 필요로 하는 환경 변수 항목을 정리합니다. 실제 비밀값은 문서에 넣지 않습니다.

**예상 변경 문서:** `docs/PRD.md`, `docs/spec.md`, `docs/plan.md`, 필요 시 `docs/setup.md`.

**확인·완료 기준:** 도구 확인 결과, 문서 차이, 결정 사항과 남은 항목을 공유합니다. 현재 단계의 결정을 막는 내용이 정리되어야 합니다. 아직 패키지 설치, 코드 작성, DB 생성은 하지 않습니다. 이후 단계의 세부 결정이 남으면 해당 Phase 전에 확인하도록 기록합니다.

### Phase 1. FastAPI와 React 뼈대 만들기

**목표:** 기능 구현 전에 화면과 API가 서로 통신하게 만듭니다.

**작업 순서**

1. `backend/` 가상환경과 Phase 0에서 선택한 최소 패키지를 준비하고 버전을 기록합니다.
2. `backend/app/main.py`에서 FastAPI 앱을 시작합니다.
3. `frontend/`에 React 프로젝트를 준비하고 선택한 도구·의존성 버전을 기록합니다.
4. React 기본 화면과 공통 스타일을 만듭니다.
5. 화면에서 FastAPI 상태 확인 요청을 보내고 결과를 확인합니다.
6. 개발 화면 주소에서 API 요청이 가능하도록 허용할 출처를 설정합니다.
7. 서버 전용 설정과 브라우저에 전달되는 설정을 분리하고 비밀값 없는 환경 변수 예시를 작성합니다.
8. 필요한 SQLite3·생성 파일 제외 규칙을 `.gitignore`에 보완합니다.

**예상 변경 파일:** `backend/requirements.txt`, `backend/app/main.py`, `backend/app/core/`, `frontend/package.json`, React 시작 파일·공통 CSS·API 요청 파일, 환경 변수 예시, `.gitignore`.

**확인 방법:** 두 개발 서버의 실행, React 화면 표시, API 요청 성공·실패 표시, 서버 비밀값이 프론트에 포함되지 않는지 확인합니다.

**완료 기준:** 두 앱이 각자 실행되고 화면에서 API 응답을 확인할 수 있습니다. 아직 회원·기록 기능은 만들지 않습니다.

### Phase 2. DB 연결 기반과 회원·인증 기반

**목표:** SQLite3로 시작하되 Supabase로 연결을 바꿀 수 있는 데이터 접근 기반을 준비합니다.

**작업 순서**

1. 환경 설정으로 DB 연결 대상을 구분합니다. 자동 테스트용 DB는 개발 DB와 분리합니다.
2. Phase 0에서 정한 연결 도구와 DB 구조 변경 관리 도구를 적용합니다.
3. 선택한 인증 방식에 따라 회원 정보와 고유 사용자 식별값을 설계합니다.
4. FastAPI 직접 인증이면 안전한 비밀번호 저장과 로그인 확인 기반을 만듭니다. Supabase Auth이면 인증 정보 확인과 앱 회원 정보의 연결 방식을 만듭니다.
5. 이메일·닉네임의 필수·중복·길이 조건은 확정된 spec을 적용합니다.
6. 운영자 권한을 일반 사용자와 구분할 기반을 정한 방식으로 준비합니다.
7. SQLite3의 초기 구조를 만들고 저장·재조회·중복 방지 테스트를 작성합니다.
8. Supabase에서도 적용 가능한 구조인지 검토합니다. Auth를 사용하면 실제 인증 연동과 로컬 대체 테스트의 차이를 기록합니다.

**예상 변경 파일:** `backend/app/db/`, `backend/app/core/`, `backend/app/accounts/`, `backend/migrations/`, `backend/tests/`, 의존성·환경 변수 예시 파일.

**확인 방법:** 회원 관련 데이터 저장·중복 차단·재실행 후 유지, 비밀번호 원문 미저장, 인증 확인과 일반 사용자·운영자 구분을 점검합니다.

**완료 기준:** 선택한 인증 방식과 DB 구조 테스트가 통과합니다. Supabase Auth를 선택했다면 SQLite3만으로 인증까지 검증했다고 표시하지 않습니다.

### Phase 3. 회원가입·로그인·닉네임 변경

**목표:** React 화면에서 회원 기능을 끝까지 사용할 수 있게 합니다.

**작업 순서**

1. 가입·로그인·닉네임 변경 FastAPI API를 만듭니다.
2. 이메일·비밀번호·닉네임을 각각 확정된 입력 조건으로 검사합니다.
3. 가입·로그인·계정 설정 React 화면을 API와 연결합니다.
4. 성공 후 이동과 실패 시 입력 보존은 확정된 spec을 적용합니다.
5. 로그인 상태 확인과 기록 화면 접근 제한을 연결합니다. FastAPI에서도 인증을 검사합니다.
6. 닉네임 변경은 본인만 가능하게 하고 공개 표시 이름 처리 기준을 적용합니다.

**예상 변경 파일:** `backend/app/accounts/`, `backend/app/core/`, `backend/tests/`, `frontend/src/pages/`, `frontend/src/api/`, 공통 메뉴·입력 컴포넌트.

**확인 방법:** 정상 가입·로그인, 입력 경계값, 중복, 잘못된 로그인, 본인만 닉네임 변경, 비로그인 직접 API 접근을 확인합니다.

**완료 기준:** spec 2~4절과 관련 공통 기준을 통과합니다. 이메일 확인과 비밀번호 찾기는 만들지 않습니다.

### Phase 4. 공부 기록·할 일·오류 기록의 데이터 구조

**목표:** 세 종류의 기록을 안전하게 저장할 기반을 만듭니다.

**작업 순서**

1. 각 기록을 작성자와 연결합니다.
2. 공부 기록에는 제목·내용·공개 여부·작성 날짜와 시간을 저장합니다.
3. 할 일에는 제목·완료 여부·공개 여부·완료 날짜와 시간을 저장합니다. 최신 작성 순서 구분에 필요한 작성 시간도 관리합니다.
4. 오류 기록에는 제목·내용·해결 방법·해결 여부·공개 여부·해결 날짜와 시간을 저장합니다. 최신순 구분에 필요한 작성 시간도 관리합니다.
5. 세 종류 모두 기본 비공개를 적용합니다.
6. 입력 길이와 해결 방법 필수 조건, 상태 전환·날짜 처리 기준을 확정된 spec대로 적용합니다.
7. DB 구조 변경과 자동 테스트를 준비합니다. 수정 날짜 표시 등 PRD에 없는 조건은 확인 후에만 반영합니다.

**예상 변경 파일:** `backend/app/records/`, `backend/migrations/`, `backend/tests/`.

**확인 방법:** 종류별 저장·조회·작성자 연결·기본값·입력 조건·상태 전환·데이터 유지와 임시 테스트 DB 분리를 확인합니다.

**완료 기준:** 데이터 테스트가 통과하고 미확정 상태 전환 규칙을 임의로 구현하지 않았습니다.

### Phase 5. 공부 기록 전체 흐름

**목표:** 공부 기록을 작성하고 나중에 다시 찾습니다.

**작업 순서**

1. 제목 1~100자·내용 1~5,000자 작성 API와 React 화면을 만듭니다.
2. 기본 비공개와 작성 시간 자동 저장을 적용합니다.
3. 내 기록 최신순 목록과 자세히 읽기를 연결합니다.
4. 내 제목·내용 검색을 연결합니다.
5. 본인만 수정·삭제할 수 있도록 API와 화면을 만듭니다.
6. 확정된 공백·성공 이동·삭제 확인·실패 안내 규칙을 적용합니다.

**예상 변경 파일:** `backend/app/records/`의 공부 기록 처리, 관련 테스트, React 공부 기록 화면·API 요청·공통 카드.

**확인 방법:** 최소·최대·초과 입력, 작성·재조회·검색·수정·삭제, 최신순, 비공개 및 다른 사용자의 변경 차단을 확인합니다.

**완료 기준:** spec 5절과 공통 권한 기준을 통과합니다.

### Phase 6. 할 일 전체 흐름

**목표:** 할 일을 작성하고 완료 상태를 관리합니다.

**작업 순서**

1. 제목 1~100자 작성·수정·삭제 API와 React 화면을 만듭니다.
2. 기본 비공개와 확정된 최초 완료 상태를 적용합니다.
3. 미완료 우선, 같은 상태 최신순으로 목록을 보여줍니다.
4. 전체·남은 일·완료한 일 필터를 만듭니다.
5. 완료·취소와 완료 날짜 처리를 확정된 기준으로 연결합니다.
6. 본인만 상태 변경·수정·삭제할 수 있게 합니다.
7. 내 할 일 검색·마감일·중요도는 만들지 않습니다. 공개 할 일 검색은 Phase 8에서 만듭니다.

**예상 변경 파일:** 할 일 API·데이터 처리·테스트와 React 할 일 화면·API 요청 파일.

**확인 방법:** 제목 경계값, 정렬, 세 필터, 완료·취소·날짜, 작성자 권한과 실패 시 표시를 확인합니다.

**완료 기준:** spec 6절을 통과합니다.

### Phase 7. 오류 기록 전체 흐름

**목표:** 미해결 오류를 저장하고 해결 과정을 남깁니다.

**작업 순서**

1. 오류 제목 1~100자·내용 1~5,000자 API와 React 화면을 만듭니다.
2. 해결 방법 없는 미해결 저장을 지원합니다. 해결 방법 입력 시 1~5,000자를 검사합니다.
3. 해결 상태에는 해결 방법을 필수로 검사합니다.
4. 해결 시간 자동 저장과 미해결 복귀 처리는 확정된 spec대로 연결합니다.
5. 최신순 목록·상세·수정·삭제와 전체·미해결·해결 필터를 만듭니다.
6. 내 오류 제목·내용 검색을 만듭니다.
7. 내용과 상태는 작성자만 바꾸게 합니다.

**예상 변경 파일:** 오류 기록 API·데이터 처리·테스트와 React 오류 기록 화면·API 요청 파일.

**확인 방법:** 세 입력 항목의 개별 경계값, 해결 방법 필수, 상태·날짜, 필터·검색·정렬과 권한을 확인합니다.

**완료 기준:** spec 7절을 통과합니다.

### Phase 8. 공개 범위·공개 기록·공개 검색

**목표:** 비공개 기록을 보호하면서 공개 기록을 공유합니다.

**작업 순서**

1. 작성자만 세 종류 기록의 공개 여부를 변경하게 합니다.
2. 로그인한 사용자에게만 공개 목록·상세 API와 React 화면을 제공합니다.
3. 공개 세 종류의 목록과 종류별 필터를 연결합니다.
4. 공개 공부 기록·할 일·오류 기록 검색을 만듭니다. 각 검색 대상 항목은 확인 후 적용합니다.
5. 공개에서 비공개로 변경하면 다른 사용자의 목록·검색·직접 접근에서도 숨깁니다.
6. 공개 정렬·현재 닉네임 표시·빈 검색어 처리는 확정된 spec을 적용합니다.

**예상 변경 파일:** 공개 기록 API·권한·검색 테스트와 React 공개 목록·읽기·검색 화면.

**확인 방법:** 작성자·다른 사용자·비로그인 상태로 세 종류를 각각 조회하고 비공개 노출 여부, 필터·검색과 직접 API 접근을 확인합니다.

**완료 기준:** spec 8~10절과 각 기록의 공개 권한 기준을 통과합니다. 비공개 유출이 있으면 다음 단계로 넘어가지 않습니다.

### Phase 9. 댓글

**목표:** 공개 공부 기록과 오류 기록에서만 댓글을 사용합니다.

**작업 순서**

1. 댓글 데이터와 작성·읽기·수정·삭제 API를 만듭니다.
2. 댓글 1~500자를 검사합니다.
3. React의 공개 공부·오류 기록 읽기에 댓글을 연결합니다.
4. 댓글 작성자만 수정하게 합니다. 댓글 작성자와 기록 작성자에게 삭제 권한을 적용합니다.
5. 비공개 전환·정렬·삭제 확인·본인 기록 댓글 여부는 확정된 spec을 적용합니다.
6. 공개 할 일 댓글과 답글은 만들지 않습니다.

**예상 변경 파일:** `backend/app/community/`의 댓글 처리·DB 구조 변경·테스트, React 댓글 컴포넌트와 관련 API 요청.

**확인 방법:** 0·1·500·501자, 작성자·기록 작성자·제3자 권한, 비로그인·비공개·할 일 대상 차단을 확인합니다.

**완료 기준:** spec 11절을 통과합니다.

### Phase 10. 좋아요

**목표:** 공개 공부 기록·오류 기록에 중복 없는 좋아요를 제공합니다.

**작업 순서**

1. 사용자와 기록별 좋아요 데이터 및 중복 방지를 만듭니다.
2. 등록·재클릭 취소 API를 React 버튼과 연결합니다.
3. 본인 좋아요 상태를 표시하고 실패를 성공으로 표시하지 않습니다.
4. 공개 할 일에는 제공하지 않습니다.
5. 전체 개수 표시·본인 기록 허용·비공개 전환 처리 등은 확정 후 적용합니다.

**예상 변경 파일:** 좋아요 데이터·API·DB 구조 변경·테스트, React 좋아요 컴포넌트와 API 요청.

**확인 방법:** 등록·취소·중복 요청, 다른 사용자 좋아요 취소 차단, 허용하지 않는 대상과 비로그인 차단을 확인합니다.

**완료 기준:** spec 12절을 통과합니다.

### Phase 11. 신고와 운영자 확인

**목표:** 신고를 저장하고 운영자가 확인합니다.

**작업 순서**

1. 공개 공부 기록·할 일·오류 기록과 공개 댓글에 대한 신고 데이터와 API를 만듭니다.
2. 신고 이유·길이·중복 제한은 확정된 spec을 적용합니다.
3. React에서 신고 요청과 성공·실패 안내를 연결합니다.
4. 신고만으로 대상을 자동 삭제하지 않습니다.
5. Phase 0에서 정한 방법으로 운영자가 신고를 확인하도록 연결합니다. 운영자 권한은 FastAPI에서 검사합니다.
6. 신고 공개 범위·비공개 전환·대상 삭제 처리는 확정 후 적용합니다. Django 관리자 화면은 사용하지 않습니다.
7. 일반 사용자 신고 내역 기능이나 별도 신고 처리 상태 기능은 추가하지 않습니다.

**예상 변경 파일:** 신고 데이터·API·권한·테스트·DB 구조 변경, React 신고 입력, 선택한 운영자 확인 방법에 필요한 파일.

**확인 방법:** 모든 허용 대상의 신고 저장, 입력 조건, 중복 정책, 비로그인 차단, 운영자만 확인 가능, 자동 삭제 없음과 저장 실패 안내를 확인합니다.

**완료 기준:** spec 13절을 통과하고 운영자가 실제로 신고 내용을 확인할 수 있습니다.

### Phase 12. 반응형 화면과 공통 실패 처리

**목표:** 컴퓨터와 휴대폰에서 일관되게 사용합니다.

**작업 순서**

1. 밝은 배경·카드·명확한 메뉴와 버튼을 React 공통 컴포넌트·CSS로 정리합니다.
2. 내 홈에서 세 기록과 계정 설정으로 이동하고 핵심 기록을 보여줍니다. 표시 기준은 확정 후 적용합니다.
3. 좁은 화면과 컴퓨터 화면에서 입력·목록·상세·댓글·신고를 확인합니다.
4. API 조회·저장·수정·삭제 실패와 권한 없음 안내를 정리합니다.
5. 입력 보존과 상태 표시가 실제 처리 결과와 맞는지 확인합니다.
6. 화면에서 숨긴 버튼을 직접 API 요청으로 우회할 수 없는지 확인합니다.

**예상 변경 파일:** React 공통 컴포넌트·화면·스타일·API 오류 처리와 관련 테스트, 필요 시 FastAPI 실패 응답 처리.

**확인 방법:** 회원부터 신고까지 컴퓨터·휴대폰에서 확인하고 버튼 겹침, 화면 잘림, 빈 결과와 실패 구분을 점검합니다. 기존 계획의 360px 이상·Chrome/Edge/Safari 최신 두 버전 범위는 사용자 확인 후 적용합니다.

**완료 기준:** spec 14절과 각 기능의 실패 처리·권한 기준을 통과합니다.

### Phase 13. Supabase 연결과 최종 통합 확인

**목표:** SQLite3 테스트뿐 아니라 실제 Supabase 연결에서도 동작을 검증하고 실행 방법을 남깁니다.

**작업 순서**

1. 사용자가 준비한 Supabase 프로젝트의 연결 정보를 서버 환경 설정에 넣습니다. 서버 전용 비밀값은 프론트나 문서에 넣지 않습니다.
2. 테스트용 Supabase 환경에 DB 구조를 적용합니다. 기존 데이터가 있는 DB는 임의로 지우거나 덮어쓰지 않습니다.
3. 선택한 연결 방식으로 FastAPI의 저장·조회·검색·시간 처리·중복 방지를 확인합니다.
4. 회원 인증 방식과 앱 데이터 연결을 실제 환경에서 확인합니다.
5. 작성자·다른 사용자·운영자·비로그인 시나리오와 공개 범위 변경을 확인합니다. 선택한 연결 경로에서 DB 접근 권한도 확인합니다.
6. SQLite3와 Supabase의 차이 때문에 깨지는 기능이 있는지 확인하고 필요한 부분을 수정합니다.
7. 로컬 데이터를 실제 DB로 옮길지는 별도 결정합니다. 자동 이전은 하지 않습니다.
8. 전체 자동 테스트와 spec의 기능별 확인 항목을 실행하고 재실행 후 데이터 유지도 확인합니다.
9. `docs/setup.md`에 설치·환경 변수·로컬 SQLite3 실행·Supabase 연결·React/FastAPI 실행·테스트 방법을 작성합니다.
10. 기존 README의 내용 보존 요청을 지킵니다. 실행 안내는 별도 setup 문서에 작성하고 README 수정이 필요하면 따로 확인합니다.

**예상 변경 파일:** DB 연결 설정·구조 변경 파일·통합 테스트, 환경 변수 예시, `docs/setup.md`, `docs/plan.md`의 진행 기록, 확인 중 필요한 기존 코드.

**최종 확인표**

- [ ] 가입·로그인·닉네임 변경이 확정된 조건대로 동작합니다.
- [ ] 공부 기록 작성·목록·읽기·검색·수정·삭제가 동작합니다.
- [ ] 할 일 작성·완료·취소·필터·정렬·수정·삭제가 동작합니다.
- [ ] 오류 작성·해결·미해결 전환·검색·필터·수정·삭제가 동작합니다.
- [ ] 세 기록의 기본 비공개와 자동 날짜 저장이 맞습니다.
- [ ] 비공개 기록이 다른 사람의 목록·검색·상세·직접 API 요청에 노출되지 않습니다.
- [ ] 공개 세 종류의 필터·검색과 비로그인 차단이 동작합니다.
- [ ] 댓글·좋아요는 공개 공부 기록과 오류 기록에서만 동작합니다.
- [ ] 댓글 권한, 좋아요 중복 방지와 취소가 정확합니다.
- [ ] 신고가 저장되고 운영자가 확인하며 신고만으로 자동 삭제되지 않습니다.
- [ ] SQLite3 테스트와 Supabase 실제 연결 확인이 각각 통과합니다.
- [ ] 앱 재실행 후 데이터가 유지됩니다.
- [ ] 컴퓨터·휴대폰에서 주요 기능을 사용할 수 있습니다.
- [ ] 비밀값·실제 DB·설치 및 생성 파일이 Git 제외 대상입니다.
- [ ] 첫 버전의 제외 기능이 추가되지 않았습니다.
- [ ] 실행 문서로 환경을 준비하고 서비스를 실행할 수 있습니다.

**완료 기준:** spec의 확인 항목과 최종 확인표를 모두 통과합니다. Supabase 연결을 아직 확인하지 않았다면 해당 항목은 미완료로 남깁니다.

## 6. 기존 계획과 spec 사이의 확인 사항

사용자가 제공한 이전 plan에는 아래의 구체적인 규칙이 있었지만 현재 spec에는 확인 필요로 남아 있습니다. 기술 변경만으로 이 제품 규칙까지 확정하지 않습니다. 기존 계획의 제안을 삭제된 요구사항으로 취급하지 않고 Phase 0에서 확인할 후보로 보존합니다.

- 이메일 필수·중복 불가, 닉네임 2~20자 및 한글·영문·숫자·밑줄 허용, 비밀번호 8~64자.
- 가입 성공 후 로그인 화면, 로그인 성공 후 내 홈으로 이동. 가입·로그인 실패 시 이메일·닉네임은 유지하고 비밀번호는 지움.
- 공개 기록과 댓글에 현재 닉네임을 표시.
- 새 할 일은 미완료, 새 오류는 미해결. 완료 취소 시 완료 시간 삭제, 미해결 복귀 시 해결 시간 삭제·해결 방법 유지.
- 글의 앞뒤 공백 제거·중간 띄어쓰기 유지, 빈 검색어는 전체 목록.
- 기록 수정 날짜 저장·표시, 저장·수정 성공 후 해당 목록으로 이동, 실패 시 입력값·기존 데이터 유지, 삭제 전 재확인.
- 공개 최신순. 공개 공부 검색은 제목·내용, 공개 할 일은 제목, 공개 오류는 제목·내용·해결 방법.
- 댓글 오래된 순서. 비공개 전환 시 댓글·좋아요를 보관하되 숨기고 재공개 시 다시 표시.
- 좋아요 전체 개수 표시와 실패 시 이전 상태·개수 유지.
- 신고 이유 1~500자·앞뒤 공백 제거, 사용자별 같은 대상 신고 1회, 신고 실패 시 이유 유지, 운영자만 신고 확인, 비공개 전환 후에도 신고 보관, 별도 처리 상태 없음.
- 반응형 확인 범위 360px 이상, Chrome·Edge·Safari 최신 두 버전.

이 목록 외에도 spec 16절의 남은 확인 사항을 해당 Phase 전에 하나씩 질문합니다. 기존 계획의 Django 관리자 확인 방식만은 새 기술 구조에 맞는 운영자 확인 방법으로 교체합니다.

## 7. 실제 진행 방법과 사용자 준비 사항

1. 첫 작업은 Phase 0입니다. 문서 대조와 설치 도구 확인부터 진행합니다.
2. 현재 사용자가 전달할 비밀번호·DB 비밀값은 없습니다. Python·Node.js 등 설치 여부는 에이전트가 먼저 확인합니다.
3. 인증 방식과 운영자 신고 확인 방법, 문서 간 미확정 조건을 관련 개발 전에 사용자와 결정합니다.
4. SQLite3로 먼저 진행하는 데 Supabase 프로젝트 생성은 필수 선행 작업이 아닙니다. 다만 Supabase Auth를 선택하면 회원 연동 시점부터 프로젝트가 필요할 수 있습니다.
5. Supabase 실제 연결 단계 전에는 프로젝트와 연결 정보가 필요합니다. 필요한 항목은 선택한 연결·인증 방식에 맞게 별도로 안내하며 실제 비밀값은 로컬 환경 설정에 입력합니다.
6. 각 Phase의 작업과 확인 결과를 공유하고 사용자 확인 후 다음 Phase로 진행합니다.
7. Git 초기화·커밋, 외부 배포, 실제 DB 데이터 이전은 이 계획만으로 자동 수행하지 않습니다.
